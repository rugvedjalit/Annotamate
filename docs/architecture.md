# Annotamate 2: architecture

This document is the source of truth for how the web version of Annotamate is built.
The REST/WebSocket contract lives in [`api.md`](api.md); the UI design lives in
[`mockups/annotator.html`](mockups/annotator.html) and [`frontend.md`](frontend.md).

## 1. Product in one paragraph

Annotamate is a self-hosted, multi-user image annotation server. An administrator installs it on any
(headless) machine that holds image datasets, creates accounts for the team, and creates **projects**
that point at image folders on that machine. Team members sign in from a browser, draw bounding boxes,
review each other's work, and talk to each other through project chat, per-image comment threads,
direct messages, @mentions and notifications. Labels are written straight to disk in YOLO, Pascal VOC
or COCO format, so training pipelines read them directly.

## 3. Runtime model

* **One process.** `annotamate serve` runs Uvicorn with a single worker. Realtime state (presence, edit
  locks) lives in memory in that process. (Multiple workers are not supported; document this.)
* **Database.** SQLite by default (`<data-dir>/annotamate.db`, WAL mode, foreign keys on). `ANNOTAMATE_DATABASE_URL`
  may point at PostgreSQL. Alembic migrations run automatically at start-up.
* **Data dir.** `--data-dir` / `ANNOTAMATE_DATA_DIR`. Default: `%LOCALAPPDATA%\Annotamate` on Windows,
  `$XDG_DATA_HOME/annotamate` or `~/.local/share/annotamate` elsewhere. Holds the DB and `cache/`
  (thumbnails, re-encoded images).
* **Roots.** `--root PATH` (repeatable) / `ANNOTAMATE_ROOTS` (os.pathsep-separated). Every project folder must
  resolve (after `realpath`) inside one of the roots. Default root: the current working directory.
* **Source of truth for labels = files on disk.** The DB stores metadata (users, projects, image index and
  status, chat, comments, notifications, activity, annotation revisions). Deleting the DB loses no labels.

## 5. Accounts, roles and permissions

* **First run.** If the DB has no users, the web UI shows a *Create administrator* screen
  (`POST /api/auth/setup`, only allowed while there are zero users). `annotamate user create --admin` also works.
  While there are no users the server generates a one-time **setup token** at start-up, logs it prominently and
  prints it in the `annotamate serve` console. Setup requests made on the server machine itself (loopback peer
  and no proxy/tunnel headers such as `X-Forwarded-For`, `Forwarded`, `X-Real-IP`, `Via`) need no token; any other
  client must send it (`setup_token`; `GET /api/auth/state` reports `setup_token_required`). The check and the
  creation of the administrator run under one lock, so concurrent setups yield exactly one administrator.
* **Global role.** `is_admin` users manage accounts, create/delete projects and can open every project as a manager.
* **Project roles** (`project_members.role`):

| Capability | viewer | annotator | reviewer | manager | admin |
| --- | :-: | :-: | :-: | :-: | :-: |
| See images, labels, stats, activity, members | ✓ | ✓ | ✓ | ✓ | ✓ |
| Project chat, image comments, @mentions | ✓ | ✓ | ✓ | ✓ | ✓ |
| Edit annotations, submit for review / mark done | | ✓ | ✓ | ✓ | ✓ |
| Claim an unassigned image (assign to self) | | ✓ | ✓ | ✓ | ✓ |
| Approve / reject submitted images | | | ✓ | ✓ | ✓ |
| Add classes | | if setting | ✓ | ✓ | ✓ |
| Rename / recolour / delete classes | | | | ✓ | ✓ |
| Assign images to others, bulk actions | | | | ✓ | ✓ |
| Members, project settings, rescan, upload, export | | | | ✓ | ✓ |
| Delete project, manage users | | | | | ✓ |

Project settings that change permissions:
* `restrict_to_assigned` (default false): annotators may only edit images assigned to them (or unassigned images, which they claim on first save).
* `annotators_can_add_classes` (default true).
* `require_review` (default false): submitting sends images to `review` instead of `done`.

Passwords: argon2id, minimum 8 characters. Deactivated users cannot sign in; their sessions are revoked.

## 6. Image workflow

Statuses: `todo` → `in_progress` → (`review` →) `done`, with `rejected` going back to the annotator.

| From | Action / event | To |
| --- | --- | --- |
| `todo`, `rejected` | first annotation save | `in_progress` |
| `todo`, `in_progress`, `rejected` | `submit` | `review` if `require_review` else `done` |
| `review` | `approve` (reviewer+) | `done` |
| `review` | `reject` (reviewer+, comment required) | `rejected` |
| `done`, `review` | `reopen` (annotator who owns it, reviewer+) | `in_progress` |

Independently: `flagged` (bool, anyone who can edit) and `assignee_id` (nullable).
When an image row is first created (index, rescan, upload), an existing label file makes it start as `done`;
otherwise `todo`. A rescan never changes the status of an existing row.

**Missing images.** A rescan does not delete rows of files that are gone: it sets `images.missing`. Missing images
are excluded from lists, neighbours, counts, statistics, exports, bulk actions, filters and project summaries
(`missing_count` reports them), keep their comments, revisions and status, and are restored when the file
reappears. A manager can purge them for good (`POST /api/projects/{pid}/prune-missing`).

## 7. Annotations on disk

* Label path: `<label_dir or image's own folder>/<image stem>.<txt|xml|json>`; `classes.txt` lives in the label dir
  (or the image dir when no label dir) and is read and written through the same root-confinement check as label
  files. Nested images (recursive projects) mirror their sub-folder under the label dir.
* **Shared stems.** Images whose path without extension is equal map to the same label file (`a.jpg` and
  `a.png`; on Windows and macOS, whose file systems ignore case, also `A.JPG`). `images.label_key` (the path
  without extension, casefolded only on those platforms; indexed with the project id, recomputed by a rescan) groups
  them: the first image in natural order owns the file; every later one is read-only, with a `readonly_reason`
  naming the owner (`409 readonly` on save/restore). Uploads of a colliding file are skipped. In YOLO projects the
  stem `classes` is reserved for `classes.txt`: such an image is read-only and its upload is skipped.
* Formats: YOLO (`class cx cy w h`, normalised, 6 decimals), Pascal VOC (XML, integer pixel coords, real depth),
  COCO (one JSON per image, compatible with the desktop app; categories 1-based). Dataset-level export is separate.
* **Class identity.** In the API boxes reference `ProjectClass.id` (stable). The class *index* (its position) is the
  YOLO id and the order of `classes.txt`. VOC/COCO use class *names*. Renaming a class in a VOC/COCO project, or
  deleting/merging any class, rewrites affected label files. A VOC/COCO rename is a background job whose work is
  recorded in `pending_renames` (committed together with the new name): until every file has been rewritten, label
  reads map the old name onto the renamed class (so saves always write the new name), creating or renaming another
  class to the old name or deleting the class is refused with `409`, and the start-up hook resumes unfinished
  renames. The record is cleared when the rewrite has finished without failures. A file that cannot be read or
  written keeps the record and the job is retried with back-off (30 s, 2, 10 and then every 30 minutes) and at once
  by a rescan.
* **Unknown labels.** A box whose label does not match a project class is returned with `class_id: null` and
  `raw_label` (the name, or the YOLO index as a string). On save, such boxes are written back with their raw label,
  so nothing is lost. GET never modifies the class list.
* **Read-only files.** YOLO lines with more than 5 values (segmentation/OBB) or unparsable files make the image
  read-only (`readonly_reason`), so saving can never destroy data the tool does not understand.
* **Hostile label files.** Parsers never raise: any malformed input (huge integers, deep nesting, wrong JSON
  shapes, invalid XML) becomes a read-only result, and indexing isolates each file so one bad file cannot stop a
  project from loading. Label files over 8 MB are not read (read-only, no boxes); files with more than 20,000
  boxes show the first 20,000 read-only. VOC files may not contain a DOCTYPE or entity declarations in any
  encoding and may nest at most 64 levels. Label text echoed into `readonly_reason` is cut to 100 characters.
* **Image formats.** Only JPEG, PNG, BMP, WebP and TIFF content is decoded (Pillow's `formats=` allow-list), whatever
  the file extension says; other formats (EPS, ICO, TGA, JPEG 2000...) are unreadable images and skipped uploads.
* **Scanning** skips symbolic links, Windows junctions and folders whose real path leaves the root.
* **Exports** stream image files in 1 MB chunks; an item that fails is skipped with a warning (the archive stays
  valid), and entries whose names contain backslashes, colons, control characters or `.`/`..` segments are
  skipped.
* **Uploaded file names** drop invisible formatting characters and avoid every Windows device name (`CON`, `COM¹`,
  `CONIN$`, `con .png`...).
* **Atomic writes.** Write to a temp file in the same folder, `fsync`, `os.replace`.
* **Multi-file rewrites** (class delete/merge, `core.fsutil.atomic_write_many`) are all-or-nothing: pre-flight
  writability check of every target (including the Windows read-only attribute), all new contents written and
  `fsync`-ed as temp files, an `fsync`-ed backup copy of every original next to it, a journal in
  `<data-dir>/journal/` (with the SHA-256 of each old and new content) written before the first replace and
  removed after the last, rollback of already replaced files if one replace fails
  (temp and backup files are always cleaned up). If the rollback itself fails the API answers
  `500 migration_incomplete` with the affected files, keeping their backups and the journal. At start-up, before
  serving, any leftover journal is rolled back: a target is restored only if it still holds exactly the content
  that run wrote and its backup matches the recorded hash; a target never replaced keeps its content, and one
  changed since (a later save) is left alone with its backup kept for inspection. Temporaries are deleted.
  Class delete/merge refuses (`400`, nothing changed) when an existing label file cannot be read.
* **Preserving unmodelled fields.** VOC and COCO saves patch the file's current document instead of rebuilding it.
  Saved boxes are mapped to the original objects/annotations through the deterministic box ids the reader hands
  out (position in the file), so each mapped element keeps its extra fields (VOC `pose`, `occluded`, custom
  elements, `source`...; COCO `attributes`, `iscrowd`, `score`, annotation/category ids, `info`, `licenses`...).
  Document-level extras are kept; new boxes use the standard shape. VOC `<path>` of a new file is the image's
  file name, never a server path.
* **Versions.** `version` = first 16 hex chars of SHA-256 of the label file bytes (`null` when no file).
  Saves send `base_version`; a mismatch returns `409 conflict` with the current content.
* **Revisions.** Every save stores a revision row (boxes JSON, user, time); the last 50 per image are kept and can be restored.
* **EXIF orientation.** Project setting `exif_mode`: `apply` (default; matches OpenCV/Ultralytics) or `ignore`.
  Reported width/height follow the mode. When an image carries an orientation tag ≠ 1 the server re-encodes it
  (transposed for `apply`, tag stripped for `ignore`) so browsers can never rotate it differently.
* **Coordinates.** Boxes travel as floats in image pixels: `x1 < x2`, `y1 < y2`, clamped to the image.

## 8. Edit locks and presence

* Opening an image in the annotator subscribes to presence. A user with edit rights requests the image's edit
  lock over the WebSocket. Locks expire after 60 s without a heartbeat (clients ping every 20 s) and are released
  on close/disconnect.
* Another user opening a locked image gets it read-only ("Alice is editing"), can still comment and chat, and
  sees the lock released live. Managers/admins can *take over* (the previous holder is notified and drops to read-only).
* The same user opening the image in a second tab moves the lock to that tab; the first tab turns read-only
  ("You are editing this image in another tab") and can take it back with *Edit here*.
* `PUT annotation` from a user who does not hold the lock while someone else holds it → `423 locked`.
  If nobody holds a lock, saves are accepted (keeps API clients working).

## 9. Communication

* **Project chat**: one channel per project, realtime, edit/delete own messages, managers can delete any,
  optional image reference ("share this image"), unread counts per member.
* **Image comments**: threads on each image, optional pin (x, y in image pixels), resolve/unresolve.
  Rejecting an image creates a comment with the reason.
* **Direct messages** between any two active users, unread counts, live read receipts ("Seen"), realtime.
* **@mentions** (`@username`) in chat, comments and DMs create notifications.
* **Notifications** (realtime + list + unread badge) for: mentions, assignments, review approved/rejected,
  new comment on an image you are assigned to or commented on, new DM.
* **Activity feed** per project: saves (coalesced to one entry per user/image per 10 minutes), status changes,
  assignments, class changes, membership changes, uploads.
* **Presence**: online users globally; per project, who is on which image (with its file name).
* **Statistics**: the overview's 30-day chart is bucketed in the viewer's calendar (the browser sends its UTC offset).

## 10. Security

* Session cookie `annotamate_session`: random 32-byte token, only its SHA-256 is stored; HttpOnly, SameSite=Lax,
  Secure when `secure_cookies`; sliding expiry (`session_days`, 14) capped by an absolute lifetime
  (`session_max_days`, 90 days after sign-in). Sessions are revoked on sign-out, password change (other sessions),
  admin password reset and deactivation, and open WebSockets of revoked sessions are closed with `4401`.
* CSRF: every non-GET/HEAD/OPTIONS request under `/api` must carry header `X-Annotamate-Client: web`
  (or any non-empty value). No CORS is configured, so browsers cannot send it cross-site.
* WebSocket: cookie auth; `Origin` must equal the `Host` header (`X-Forwarded-Host` is ignored, it could come from
  the client) and be `https` when `secure_cookies` is on. Per socket: 20 frames/s with bursts of 40 (excess dropped,
  persistent flooding closed with `1008`), `typing` relayed at most every 2 s per target, typing/presence skipped
  for recipients with a backed-up queue, ids bounded to positive 64-bit integers, malformed or deeply nested JSON
  answered with `bad_request`. At most 10 sockets per user and 5000 in total (`4429`).
* Login rate limit (sliding 10 minutes, `429`): 10 failed attempts per (address, username); 30 per address across
  usernames (`ANNOTAMATE_LOGIN_IP_LIMIT`, 0 = off), with IPv6 counted per /64 and loopback/private addresses allowed
  10 times as many (a proxy without trusted forwarding headers, Docker's gateway or an office network can make every
  user share one address); 100 per username across all addresses, so rotating addresses gains nothing. An attempt is
  recorded atomically **before** the password is verified (parallel guesses cannot exceed the limit) and taken back
  when the password is right. Usernames that no account can have share one bucket. When the limiter's table is full,
  expired entries go first and address-wide entries are never evicted early.
* Password hashing: argon2id (library defaults), at most four hashes/verifications at a time; at most 16 requests to
  the hashing routes (sign-in, setup, password changes, account creation) are admitted at once, more get
  `503 busy` immediately instead of tying up worker threads.
* First-run setup without the token only for requests made on the server itself: loopback peer, no proxy/tunnel
  headers, a `Host` of `localhost`/`127.0.0.1`/`[::1]` (a DNS-rebinding page sends its own name) and a matching
  `Origin`.
* Accounts: an administrator cannot reset their own password through the admin route (the account page asks for the
  current one); admin-right and account-status changes are serialised and the last active administrator cannot be
  demoted or deactivated.
* A one-time warning is logged when requests carry an `X-Forwarded-For` that uvicorn did not apply (the proxy is not
  in `FORWARDED_ALLOW_IPS`).
* Request size limits (ASGI middleware, `413 too_large`, checked against `Content-Length` and the streamed byte
  count): 2 MB for ordinary routes (`ANNOTAMATE_MAX_BODY_MB`), 64 KB for `PUT /api/me/settings`,
  `ANNOTAMATE_MAX_UPLOAD_REQUEST_MB` (1024) for the upload route, plus `ANNOTAMATE_MAX_UPLOAD_MB` per file.
* Images: a pixel budget (`ANNOTAMATE_MAX_IMAGE_MEGAPIXELS`, default 150) is enforced when an image is probed,
  uploaded or fully decoded (over-budget images report an `error` and are skipped by uploads); at most three full
  decodes run at once and concurrent requests for the same thumbnail/re-encoded image decode it only once.
* `base_url` is validated at start-up (`^/[A-Za-z0-9._~\-/]*$`, no `.`/`..` segments, normalised to a trailing
  slash) and HTML-escaped where it is injected into the page.
* Edit locks: one per WebSocket connection and at most three per user; on every `ping` the session is re-validated
  (close `4401` when expired) and the right to edit each locked image is re-checked (`lock.revoked` with `by: null`
  when it was lost, e.g. after reassignment under `restrict_to_assigned`).
* Archived projects are read-only: no annotation saves, reviews, class or assignment changes, bulk actions or
  uploads (`403`); chat, comments, settings, members, export and restoring still work.
* Notifications of a project the recipient has left keep their text but lose the project and image link; review
  results go only to annotators who still have access.
* Filesystem: project folders and every served/written file are resolved with `realpath` and must stay inside
  the roots / project folders. The client never sends paths except in the admin-only folder browser and project
  creation, both validated against the roots.
* Uploads: manager-only, image extensions only, size-limited, filenames sanitised, never overwrite (suffix `-1`, `-2`…).
* Security headers: `X-Content-Type-Options: nosniff`, `Referrer-Policy: same-origin`,
  `X-Frame-Options: DENY`, `Cross-Origin-Opener-Policy: same-origin`, `Cross-Origin-Resource-Policy: same-origin`,
  a restrictive `Permissions-Policy`, `Strict-Transport-Security` (one year) when `secure_cookies` is on, and a
  strict `Content-Security-Policy` for the SPA (self only: `connect-src 'self'`, which covers the same-origin
  WebSocket; `img-src 'self' blob: data:`). API responses default to `Cache-Control: no-store`.
* `GET /api/openapi.json` needs a signed-in user.
* Names: invisible formatting characters (bidirectional overrides and isolates, zero-width spaces, BOM, soft hyphen)
  and control characters are removed from display names and project names and refused in class names; chat shows
  `@username` next to display names; message links stop at such characters.
* `GET /api/users` returns the full `User` to administrators only; everyone else gets `UserBrief & {online}`.

## 11. Frontend summary

React 19 + TypeScript (strict) + Vite, Tailwind CSS 4, Radix primitives (`radix-ui`), lucide icons, TanStack Query
(server state), Zustand (UI/realtime state), TanStack Virtual (100k-row lists), React Router, sonner (toasts),
cmdk (command palette). Fonts bundled (Inter, JetBrains Mono) so it works offline. Details: [`frontend.md`](frontend.md).

## 12. Quality bar

* Python: ruff, pytest. Every API endpoint has at least one test; permission rules and path safety have dedicated tests.
* TypeScript: `tsc -b` clean, ESLint clean, Vitest for pure logic (geometry, history, keymap, save state machine).
* E2E: Playwright suite against the real server and the built SPA (`web/e2e`, one fresh server per run plus a
  second one under a URL prefix): first-run setup, accounts, project roles, annotating with mouse and keyboard
  (YOLO file checked on disk), edit locks and presence, the review workflow, chat/DM/comments/notifications,
  assignments, uploads, archive, export and the sub-path deployment. Every page fails the test on console errors,
  warnings or uncaught exceptions (CSP violations included).
* CI runs all of it plus a wheel build + install smoke test and a Docker build.
